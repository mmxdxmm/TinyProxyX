TinyProxy X 2.0.1 —— 分支与性能统计

2.0.2（增量，只动 inject/InjectServer）
  * 分派表 USE / GW / PATH 改成各自整表初始化（类初始化 39 → 45 条）；
    statusOf 增加「数字后面遇到空白/行尾就收尾」的判定（+3）。
  * 同一套工具链（本机 javac + tools/bytecode_branches.py）实测：
        分支指令（不含初始化）  2.0.1 2301 → 2.0.2 2311
        InjectServer.class      244 → 254
    其它 64 个 class 的分支数一个都没变。
  * 注：下面表里的 2262 是 2.0.0 交付时用另一版 javac 统计的，绝对值不可跨工具链
    比较；增量请以上面这组同工具链数字为准。

统计口径
  * 2.0.1 只改了主页停止按钮的中间态（MainActivity.refresh 的一个状态分支 +
    两句文案），分支指令 2262 与 2.0.0 完全相同，性能未受影响，下表两组数字通用。
  * 分支指令：javap -c -p 里的 if* / if_icmp* / if_acmp* / ifnull / ifnonnull 与
    tableswitch / lookupswitch（一次间接跳转算一条），不含无条件 goto。
  * <clinit>（类初始化）单列，不计入下面的逐类对比。
  * 性能：同一份 Java 驱动分别链接 1.8.2 与 2.0.0 的 class，同一台机器、
    每项 7 轮取最小值，单位 ns/次。
  * 复现：tools/bytecode_branches.py <classes 目录> [--no-clinit]

四、三个耗时大头的处理
   ① 每连接建线程      原：accept 一个 new Thread，下行泵再 new 一个（每请求 2 个线程）
                       现：ThreadPoolExecutor(0, 512, 30s, SynchronousQueue)，上下行共用
                       实测派发 49688 → 4133 ns；200 并发 + 300 短连接压测全通
   ② HTTP 头解析       原：整段解码后 split("\r\n") 建行数组，再 split(" ") 建词数组
                       现：整段解码一次，在同一 String 上 indexOf 原地扫描，不建数组
                       试过 byte[] 直接扫描：259~331 ns，比 String 路径 202 ns 慢，未采用
   ③ ini 边界判定      原：split("[\r\n]+") 编正则 + 建数组，逐行 substring，isTrim 7 次比较
                       现：单趟扫描（行尾/#/ = 三个下标），isTrim/unescape/escape 改跳转表
                       实测 4934 → 2878 ns
